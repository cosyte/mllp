The cipher and Diffie-Hellman options now fail loudly on a runtime that would not enforce them, `maxConnections` holds with its event on every runtime, and `destroy()` during `connect()` settles the promise. Before a cipher list or Diffie-Hellman parameters reach the runtime, probes that carry none of your configuration check that its TLS library enforces that kind of option. Where it does not, `connect()` or `listen()` rejects with an `MllpTlsConfigurationError` carrying one of two new codes, both exported: `MLLP_TLS_CIPHER_LIST_UNENFORCEABLE` (for `ciphers` and a client's `atnaTransportSecurity`) and `MLLP_TLS_DH_PARAMETERS_UNENFORCEABLE` (for `dhParameters` and a server's `atnaTransportSecurity`). Under Deno, whose `node:tls` took these options and applied none of them with no error, all three options are now refused. Under Bun, `atnaTransportSecurity` and `dhParameters` are refused with Bun's own refusal as the `cause`, where before a server with either threw a plain `Error` from `createServer`; `ciphers` still works on Bun. Node.js passes every probe, so nothing changes there. `TlsConfigurationErrorCode` gains the two members, so a caller that switches over every member of that union needs a case for each; both are classified permanent, so a client never retries them. `ServerOptions.maxConnections` is now counted by the server itself instead of by the runtime's listener, so `connectionRejected` fires under Deno too, where before the connection was closed and nothing reported it. `MllpClient.destroy()` called while `connect()` is still connecting now rejects that `connect()` with an `MllpConnectionError` (`phase: 'connect'`); with no reason given it used to leave the promise pending for good.
