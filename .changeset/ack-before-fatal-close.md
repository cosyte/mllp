**A frame delivered before a refused one is still acknowledged before the connection closes, so the sender does not resend a message already committed.** When a good frame and a frame with a fatal framing error arrived in the same read (a sender that writes its next frame before the previous acknowledgement arrives), the good frame reached the handler but the connection closed at once on the error, before the acknowledgement went out, even for a synchronous handler; the sender resent the message and it was processed twice. Now, on a fatal framing error, the connection reads nothing more, moves to `DRAINING`, waits for every delivered frame's handler to settle and its acknowledgement to be written (`AA`, a negative ACK for a handler that throws, a custom builder's bytes, or a manual-mode handler's own `send`), then moves to `CLOSED` and ends the socket gracefully. The wait is bounded by `drainTimeoutMs` (30 seconds by default, `ServerOptions.drainTimeoutMs` on a server): a handler still running then is abandoned and the socket destroyed, so a handler that never settles cannot hold the connection open. With nothing running, the connection is destroyed at once as before. New: `Connection.holdOpenFor(work)` registers the work answering a delivered frame; `MllpServer` calls it for every message, and a caller driving a bare `Connection` may call it too. What a caller sees: on a server with a handler still running, a fatal framing error now shows `CONNECTED` to `DRAINING` to `CLOSED` on `'stateChange'` instead of `CONNECTED` to `CLOSED`, and the `'close'` event comes once the answers are out. Nothing a caller must change.
