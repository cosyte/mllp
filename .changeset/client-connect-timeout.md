A client can now bound how long it waits to establish a connection. New option `ClientOptions.connectTimeoutMs` (also on `createStarterClient`): an integer number of milliseconds from 1 to 2147483647 that covers the TCP connect and, with TLS on, the handshake after it. Unset means no bound, the behaviour so far, in which a connect to an address that drops packets waits on the operating system and a TLS handshake against a peer that accepts the TCP connection and never answers waits indefinitely. On expiry the socket is destroyed and `connect()` rejects with an `MllpConnectionError` whose `phase` is `connect` and whose `connectionCause` is the new `connect-timeout`; nothing was written, so no message can have reached the peer. On an auto-reconnect attempt the expiry feeds the reconnect policy like any other connect failure: `RetryContext.lastError` carries `code: "ETIMEDOUT"` and it is classified transient, so the client backs off and tries again. `ConnectionErrorCause` gains the member `connect-timeout`, so a caller that switches over every member of that union needs a case for it. A `connectTimeoutMs` that is not an integer in range throws a `RangeError` when the client is created.
