**`server.close()` waits for the handlers still running and sends their ACKs before it closes each connection, so a graceful shutdown no longer makes the sender resend a message already committed.** A shutdown during a slow `onMessage` commit used to end the connection at once: the handler finished its commit, but its ACK was never sent, the sender resent the message, and it was processed twice. Now `close()` reads nothing more on each connection (bytes a sender writes from then on are dropped unread, so no new message reaches a handler), waits for every handler still running and the ACK it writes (`AA`, a negative ACK for a handler that rejects, a custom builder's bytes), then ends the socket gracefully. In manual mode the wait lasts until the handler's promise settles, so send the ACK before the handler returns or resolves. In custom-ACK mode the `onMessage` observer is not waited for, since it writes no ACK. A connection accepted after `close()` began (a TLS handshake that finished during the wait) is closed at once, unread. The wait is bounded by `drainTimeoutMs` (30 seconds by default): work still running then is abandoned, its connection destroyed, and an `MllpConnectionError` with `phase: 'close'` on `'error'` counts per message how many were delivered without their ACK being sent, how many manual-mode handlers may not have sent theirs, and, separately, how many observers were still running. The same report is made when the sender closes or half-closes the connection before that work settles, since its ACK can then not reach it. An ACK whose handler settles after its connection has closed is now reported as `ACK not sent: the connection closed before the handler settled`, no longer as socket backpressure. On a bare `Connection`, `close()` now also waits for the work passed to `holdOpenFor()`, which takes a new optional `{ kind: 'ack' | 'manual' | 'observer' }` saying what that work owes the peer (`'ack'` by default, as before; `close()` does not wait for an `'observer'`), and the new `stopReading()` drops every byte that arrives from then on. What a caller sees: `server.close()` takes as long as the slowest handler still running, up to `drainTimeoutMs`. Nothing a caller must change.
