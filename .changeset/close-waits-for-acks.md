**`server.close()` waits for the handlers still running and sends their ACKs before it closes each connection, so a graceful shutdown no longer makes the sender resend a message already committed.** A shutdown during a slow `onMessage` commit used to end the connection at once: the handler finished its commit, but its ACK was never sent, the sender resent the message, and it was processed twice. Now `close()` reads nothing more on each connection (bytes a sender writes from then on are dropped unread, so no new message reaches a handler), waits for every handler still running and the ACK it writes (`AA`, a negative ACK for a handler that rejects, a custom builder's bytes), then ends the socket gracefully. In manual mode the wait lasts until the handler's promise settles, so send the ACK before the handler returns or resolves. The wait is bounded by `drainTimeoutMs` (30 seconds by default): a handler still running then is abandoned, its connection destroyed, and an `MllpConnectionError` with `phase: 'close'` on `'error'` says how many handlers were still running and that their ACKs were not sent. An ACK whose handler settles after its connection has closed is now reported as `ACK not sent: the connection closed before the handler settled`, no longer as socket backpressure. On a bare `Connection`, `close()` now also waits for the work passed to `holdOpenFor()`, and the new `stopReading()` drops every byte that arrives from then on. What a caller sees: `server.close()` takes as long as the slowest handler still running, up to `drainTimeoutMs`. Nothing a caller must change.
