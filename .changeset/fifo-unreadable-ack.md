**A client correlating in order no longer settles a send on a frame that is not an acknowledgment without saying so.** In FIFO mode, the default, the oldest pending send is settled by whatever frame arrives next, and before this a lone `0x06` or `0x15` byte, an `MSH` with no `MSA`, or an MSA-1 outside HL7 Table 0008 resolved `send()` with no signal at all. Now the client emits the `'warning'` `MLLP_ACK_FIFO_MSA1_UNREADABLE` (an `AckModeWarning` carrying `msa1Bytes` and `byteOffset`, never field content) whenever the frame that settles a send has no readable MSA-1. What a caller sees by default: `send()` still resolves with the frame, exactly as before, plus that one warning; a `'warning'` handler that checks for an exhaustive set of codes has to allow the new one. What a caller may change: the new client option `fifoUnreadableAck: "reject"` (also on `createStarterClient`) makes such a send reject with the new `MllpUnreadableAckError` instead, whose `msa1Bytes`, `byteOffset` and `elapsedMs` are numbers only; the frame still takes that send's turn, so the next send settles on the next frame. `fifoUnreadableAck` takes `"warn"` (the default) or `"reject"`, and any other value throws a `TypeError` at construction. With `correlateByControlId: true` nothing changes: such a frame matches no send and settles nothing, and correlating by control ID remains what we recommend whenever the peer echoes MSH-10 in MSA-2.
