**The `tls` options are copied when a client or server is created.** Both kept the caller's `tls` object, and a client read it again on every connect and reconnect, so a `pfx` added to that object after construction reached the socket without the `MLLP_TLS_CREDENTIAL_CONFLICT` check and its certificate was presented in place of `cert`. Now `createClient`, `createServer` and both constructors take a copy, check it, and use only it. The copy reads each TLS option by name, so options a class instance supplies through getters, or an object inherits from its prototype, are kept (a server given `clientAuth: "MUST"` that way still requires a client certificate); it takes new arrays and new bytes for every `Buffer`, so bytes overwritten in place after construction no longer change the identity a client presents on reconnect. A caller who changed their `tls` object, its `Buffer` bytes, or put a new one in the options, to have a running client pick up new TLS settings must create a new client instead. A `tls` that is `null` or not an object now throws `MllpTlsConfigurationError` with the new exported code `MLLP_TLS_OPTIONS_NOT_AN_OBJECT` at creation, where it threw a bare `TypeError` (or, for a value such as `false` on a client, was taken as TLS with default options). The opening of the TLS section in the warning and error codes page now says which codes are thrown at creation rather than rejecting `connect()` or `listen()`.
